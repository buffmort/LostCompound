## 为什么

实测（探针 probe_rooms，每层 300 次生成取平均）：

| 层 | 尺寸 | 可走房间 |
|---|---|---|
| 1–2 | 5×5 | ~23 |
| 3–4 | 6×6 | ~34 |
| 5–6 | 7×7 | ~47 |
| 7–8 | 8×8 | ~62 |
| 9–10 | 9×9 | ~79 |

每层平均：**战斗房 32 · 空房 16 · 合成房 0.5 · 宝箱房 0.5**

**10 层合计 ≈ 490 个房间，其中 ≈ 320 场战斗。**

对比：Slay the Spire ~50 场、FTL ~40 场。现在一局通关约 2~4 小时，且后半程是纯疲劳。

## 现状（`Maps\TreeMazeGenerator.cs`）

- `Generate()` → `Carve(0,0,visited)`：**递归回溯迷宫**（DFS 挖通）。
- 后果：整张图是一棵**树**，任意两格之间**只有一条路** —— 没有环、没有捷径，
  走到 Boss 必须经过路径上的每一格，"绕不绕"根本不是一次决策。
- 房间分配（`InitializeRooms`）：
  - `_rng.Next(3)`：0/1 → `FightRoom`（2/3），2 → `EmptyRoom`（1/3）
  - 50% 概率放 1 个 `CraftRoom`（会先被 TreasureRoom 覆盖掉，所以两者基本互斥）
  - 50% 概率放 1 个 `TreasureRoom`
- 起点固定在 `[0][0]`，Boss 固定在 `[rows-1][cols-1]`。

## 要做的事

### 1) 布局改成「以撒的结合」式
以撒的布局特征（按用户的理解为准，实现前先跟用户确认细节）：
- 房间是**成片**的、房间之间**有多个连接**（成环），不是一条长廊；
- 从起点到 Boss 有多条路可选，绕路/直冲是真实决策；
- 有些房间是「死胡同」，值得探索但也有代价。

实现方向（待选，明天和用户定）：
- **A. 迷宫后加环**：先 DFS 生成树，再随机打通 N 条「墙」形成环（改动最小，仍用现有房间网格）。
- **B. 房间图 → 网格铺设**：先生成一张「房间图」（节点 + 边，可含环），再映射到网格并开门。
  更接近以撒，但改动大，且要处理「房间图放不进网格」的情况。
- 注意：网格尺寸在小层（5×5）里空间很紧，环的数量要按尺寸缩放。

### 2) 降低战斗比例
- 现在 `Fight : Empty = 2 : 1`。用户要「减少战斗比例」，具体数值明天定
  （建议先试 1:1，再按实测房间数微调）。
- 目标：**一局通关 60~80 场战斗**（约 40 分钟）。

## ⚠️ 必须做的一步（很容易漏）

**动了建图逻辑 → `TreeMazeGenerator.GeneratorVersion` 必须 +1。**
原因见该常量注释：种子的全部意义是「同种子 + 同算法 = 同一张图」，
改了掷点顺序/概率后旧存档会算出**另一张地图**（玩家可能站进墙里、宝箱房凭空消失，且不报错）。
+1 之后旧档会被明确拒绝，而不是安静地变成另一张图。

## 验证方式

1. 写探针统计：每层平均房间数 / 战斗房数 / 环的数量（度数 > 树形特征）/ 起点到 Boss 的路径数。
2. 确认 `GeneratorVersion` 已 +1。
3. 跑一局确认：5×5 的小层不会因为「加环」而变得拥挤或开门冲突。
4. 存档往返仍正常（旧档被拒绝，新档能读）。
